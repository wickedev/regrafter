## 기능 개요

### 컴포넌트 인라인화란?

컴포넌트 인라인화는 다음과 같이 변환합니다:

```tsx
// 변환 전
function Button({ text, onClick }) {
  return <button onClick={onClick}>{text}</button>;
}

function App() {
  return <Button text="클릭하세요" onClick={handleClick} />;
}
```

다음과 같이 변환:

```tsx
// 변환 후
function App() {
  return <button onClick={handleClick}>클릭하세요</button>;
}
// Button 컴포넌트 제거됨
```

### 사용자 요구사항

이해관계자 의견을 바탕으로:

- ✅ **리팩토링 워크플로우**: 컴포넌트 계층 평탄화
- ✅ **모든 컴포넌트 유형**: 단순, 훅, 상태/효과, 크로스 파일
- ✅ **Props 처리**: 인라인 표현식으로 유지 (변수 추출 없음)
- ✅ **정리**: 항상 원본 컴포넌트 제거 (공격적 모드)

### 범위

#### 포함 범위
- ✅ 단순 프레젠테이셔널 컴포넌트
- ✅ React 훅이 있는 컴포넌트 (useState, useEffect, useRef 등)
- ✅ 복잡한 상태와 효과가 있는 컴포넌트
- ✅ 크로스 파일 컴포넌트 인라인화
- ✅ 공격적 컴포넌트 제거
- ✅ 전이 종속성 해결

#### 제외 범위
- ❌ 클래스 컴포넌트 (함수형 컴포넌트에 집중)
- ❌ HOC 언래핑
- ❌ React.memo/forwardRef 인라인화 (안전상 명시적으로 거부)

### 높은 복잡도 요인

#### 1. 훅 병합 (복잡도: 9/10)

**과제**:
- React 훅 규칙 준수 (최상위 수준만, 일관된 순서)
- 의존성 배열 치환 (props → 실제 값)
- 상태 변수 이름 충돌 해결
- 효과 타이밍 보존
- 정리 함수 처리

**예시**:
```tsx
// 자식 컴포넌트
function Modal({ isOpen, onClose }) {
  const [count, setCount] = useState(0);
  useEffect(() => {
    // Props를 사용하는 효과
  }, [isOpen, onClose]);
}

// 부모로 인라인화 후 (부모가 이미 'count'를 가지고 있음)
function Parent() {
  const showModal = true;
  const handleClose = () => {};

  // 충돌 방지를 위해 이름 변경
  const [count_Modal, setCount_Modal] = useState(0);

  // 의존성 배열 치환
  useEffect(() => {
    // 효과 본문
  }, [showModal, handleClose]); // Props가 실제 값으로 대체됨

  // ... 컴포넌트의 나머지
}
```

#### 2. 크로스 파일 작업 (복잡도: 8/10)

**과제**:
- 다중 파일 파싱 및 변환 조정
- 전이 import 해결
- Import 충돌 감지 및 해결
- 사용 감지를 통한 공격적 컴포넌트 제거
- 비어있을 때 파일 삭제

**예시**:
```tsx
// components/Button.tsx
import { Icon } from './Icon';
export const Button = ({ text }) => <button><Icon />{text}</button>;

// pages/Home.tsx
import { Button } from '../components/Button';

// 인라인화 후:
// - Button 구현이 Home.tsx로 이동
// - Icon import가 Home.tsx에 추가됨
// - Button.tsx가 삭제됨 (다른 export가 없으면)
```

#### 3. Props 치환 (복잡도: 7/10)

**과제**:
- 변수 없이 인라인 표현식 치환
- 구조 분해 패턴
- 기본값
- 스프레드 연산자
- Props의 복잡한 표현식

**예시**:
```tsx
// 기본값과 구조 분해가 있는 컴포넌트
function Card({ title = "기본값", children, ...rest }) {
  return <div {...rest}><h1>{title}</h1>{children}</div>;
}

// 사용
<Card title={user.name} className="card">{content}</Card>

// 인라인 후 (props가 직접 치환됨)
<div className="card"><h1>{user.name}</h1>{content}</div>
```

## 구현 단계

### 1단계: 단순 컴포넌트 인라인화 (3주)

**기간**: 15일 (3주)
**팀**: 엔지니어 1명
**결과물**: 프레젠테이셔널 컴포넌트의 기본 인라인화

#### 구축할 구성요소

1. **`src/analyzer/component-detector.ts`** (3일)
   - React 컴포넌트 식별 (function/arrow)
   - 컴포넌트 분류 (단순, 훅, 복잡)
   - 인라인 가능성 감지 (훅 없음, 상태 없음 등)
   - 컴포넌트 메타데이터 추출

2. **`src/transformer/prop-substituter.ts`** (4일)
   - JSX 호출 지점에서 prop 값 추출
   - 구조 분해 패턴 처리
   - 기본값 처리
   - 스프레드 연산자 처리
   - 컴포넌트 JSX에서 props 치환

3. **`src/transformer/component-inliner.ts`** (3일)
   - 인라인화 작업 조정
   - 컴포넌트 호출을 인라인 JSX로 대체
   - 컴포넌트 정의 제거
   - 검증기와 조정

4. **`src/analyzer/inline-validator.ts`** (2일)
   - 사전 검증 체크
   - 컴포넌트 유형 검증
   - 인라인 가능성 체크
   - 오류 메시지 생성

5. **공개 API** (`src/index.ts`) (1일)
   ```typescript
   export function inline(
     files: FileInput[],
     componentFile: string,
     componentName: string,
     options?: InlineOptions
   ): Result<Code[], RegraffError>;
   ```

6. **통합 테스트** (2일)
   - 단순 컴포넌트 인라인화 테스트
   - Props 치환 테스트
   - 컴포넌트 제거 테스트
   - 오류 케이스 테스트

#### 수용 기준

- ✅ 프레젠테이셔널 컴포넌트 인라인화 가능
- ✅ Props가 올바르게 치환됨
- ✅ 컴포넌트 정의가 제거됨
- ✅ 90% 이상 테스트 커버리지
- ✅ 모든 테스트 통과

### 2단계: 복잡한 컴포넌트 인라인화 (3.5주)

**기간**: 18일 (3.5주)
**팀**: 엔지니어 1명
**결과물**: 훅과 상태가 있는 컴포넌트 지원

#### 구축할 구성요소

1. **`src/strategies/hook-merger.ts`** (5일)

   - 훅 바인딩 복제 및 이름 변경
   - 순서를 유지하면서 훅 시퀀스 병합

3. **`component-inliner.ts`의 훅별 작업** (4일)

   - useEffect 처리 (정리 포함)

   - useMemo/useCallback 처리
   - 커스텀 훅 처리

4. **의존성 배열 치환** (3일)
   - 의존성 배열에서 props 식별
   - 호출 지점의 실제 값으로 치환
   - 복잡한 표현식 처리
   - 정확성 검증

5. **통합 테스트** (3일)
   - useState가 있는 컴포넌트 테스트
   - useEffect가 있는 컴포넌트 테스트
   - 이름 충돌 테스트
   - 의존성 배열 치환 테스트
   - 커스텀 훅 테스트

#### 주요 과제

- ✅ useState가 있는 컴포넌트 인라인화 가능
- ✅ useEffect가 있는 컴포넌트 인라인화 가능
- ✅ 여러 훅이 있는 컴포넌트 인라인화 가능
- ✅ 이름 충돌이 올바르게 해결됨

| 타입 export 문제 | 낮음 | 중간 | 낮음 | 원본에 타입 유지 |

### 높은 위험 영역

#### 1. 훅 의존성 배열 치환

**위험**: 잘못된 치환으로 React 효과가 깨짐

**완화 방안**:
- 실제 시나리오를 사용한 광범위한 단위 테스트
- 치환의 AST 수준 검증
- 대체 방안: 치환이 모호하면 오류 반환

#### 2. 크로스 파일 순환 Import

**위험**: 인라인화로 순환 종속성 사이클 생성

**완화 방안**:
- Import 그래프를 사용한 사전 순환 감지
- 명확한 오류 메시지와 함께 작업 거부
- 대안 접근법 제안
